## Einrichten

    git clone <repository> /opt/geodaten-import-pipeline && cd /opt/geodaten-import-pipeline
    cp .env.beispiel .env && chmod 600 .env       # je Rolle ein eigenes Passwort: openssl rand -base64 24
    docker compose up -d db                       # Testumgebung: legt beim ersten Start die MOSIDI-Tabellen an
    docker compose run --rm einrichten            # pipeline_meta, Rollen und Rechte nach config/quellen.yaml
    docker compose run --rm pipeline --probelauf  # alles lesen und prüfen; keine dauerhaften Datenänderungen, Prüfbericht und Cache werden geschrieben
    # (Lieferkonfiguration mit INKAR im Vollumfang: rund 2 bis 3 h; schneller erst --config /app/config/pruefkonfiguration.yaml --probelauf --alle, E51)
    sudo cp deploy/systemd/geodaten-import*.{service,timer} /etc/systemd/system/
    sudo systemctl daemon-reload && sudo systemctl enable --now geodaten-import.timer
    systemctl list-timers geodaten-import.timer   # nächster Lauf

Liegt das Repository nicht unter `/opt/geodaten-import-pipeline`, `WorkingDirectory` in `geodaten-import.service` anpassen. Im Compose-Setup von MOSIDI (Betrieb bei der TH) stattdessen `deploy/mosidi/geodaten-import-mosidi.service` als `geodaten-import.service` einsetzen; sie läuft gegen `brandenburg_db` (siehe `deploy/mosidi/README.md`).

Die MOSIDI-Tabellen der Testumgebung entstehen nur auf einem **leeren** Datenbank-Volume (`sql/mosidi/` läuft über `docker-entrypoint-initdb.d`). `einrichten` ist unabhängig davon und läuft beliebig oft.

**`einrichten` setzt die Schreibrechte auf den Sollstand** (E46): Rechte der Importrolle zum Einfügen, Ändern und Löschen außerhalb von `pipeline_meta`, die nicht aus der übergebenen Konfiguration folgen, entzieht es (etwa eine Spalte, die nicht mehr zugeordnet ist, oder eine Tabelle ohne Ziel). Beschreiben mehrere Konfigurationen dieselbe Datenbank mit derselben Importrolle, `einrichten` deshalb immer mit allen aufrufen (`--config a.yaml --config b.yaml`), sonst verlieren die Ziele der übrigen ihre Rechte. Lesen und die Rechte anderer Rollen fasst es nicht an. Dazu gehören auch Sequenzen (`USAGE`, `UPDATE`): Eine Sequenz, die zu keinem Ziel mehr gehört, kann die Importrolle danach nicht mehr weiterzählen. **Grenze:** `REVOKE` entzieht nur Rechte, die der ausführende Administrator vergeben hat, als Superuser nur die, die der Eigentümer der Tabelle vergeben hat. Ein Recht, das eine andere Rolle vergeben hat (etwa ein Nicht-Eigentümer mit `GRANT OPTION`), bleibt stehen. Hat ein Administrator ohne Superuser-Rechte auf einer Tabelle selbst kein Recht, scheitert dort das `REVOKE`. Seit der Nachprüfung zu E46 bricht `einrichten` daran nicht mehr ab: Jedes `REVOKE` läuft in einem eigenen Sicherungspunkt. Danach liest `einrichten` die Rechte neu und schreibt jedes, das über den Sollstand hinausgeht, als Warnung ins Protokoll, mit der Rolle, die es vergeben hat („pipeline_import behält auf … Schreibrechte …: INSERT von …“). Entziehen kann es nur diese Rolle.

**Katalog von MOSIDI** (Antwort 75, E46): Nach einem Lauf mit Änderungen aktualisiert die Pipeline die Materialized View `public.source_granularities`, damit neue Indikatoren im Katalog erscheinen (`table_metadata` pflegt sie je Quelle selbst). `REFRESH` darf nur der Eigentümer der View; deshalb legt `einrichten` die Funktion `pipeline_meta.katalog_aktualisieren()` an: Sie gehört dem Administrator, der `einrichten` **zuerst** ausgeführt hat (`CREATE OR REPLACE` lässt Eigentümer und Rechte einer vorhandenen Funktion stehen), läuft mit dessen Rechten (`SECURITY DEFINER`, fester `search_path`), hat keine Parameter und aktualisiert nur genau diese View; ausführen darf sie nur `pipeline_import`. `einrichten` deshalb zum ersten Mal als Eigentümer der View oder als Superuser ausführen. Bei jedem Aufruf prüft es, ob der **Eigentümer der Funktion** die View aktualisieren darf: als ihr Eigentümer, als Mitglied von dessen Rolle, als Superuser oder ab PostgreSQL 17 mit `MAINTAIN`. Sonst warnt es mit der Abhilfe, als Superuser `ALTER FUNCTION pipeline_meta.katalog_aktualisieren() OWNER TO <Eigentümer der View>` auszuführen (ab 17 alternativ `GRANT MAINTAIN ON public.source_granularities TO <Eigentümer der Funktion>`). `einrichten` nur erneut auszuführen ändert den Eigentümer nicht. Nach dem `ALTER FUNCTION … OWNER TO` kann `einrichten` nur noch ein Superuser oder ein Mitglied dieser Rolle ausführen, weil `CREATE OR REPLACE` den Eigentümer verlangt. Fehlt die View (wie im mitgelieferten Schema `sql/mosidi/`, das sie nicht enthält), steht im Bericht nur ein Hinweis. In MOSIDI legt das Backend die View an (`services/backend/src/db_table_metadata/script.py`: `SELECT DISTINCT source, indikator, granularity FROM dashboard_data_de` mit eindeutigem Index); gegen diese Fassung lief die Aktualisierung im Compose-Lauf am Abgabestand (`beispielberichte/pruefstand-2026-11-05-e46/mosidi-compose/`, View danach 13 Zeilen). Scheitert die Aktualisierung (Rechte, Sperre länger als 10 s), steht eine Warnung im Bericht, `--status` meldet WARNING und der Lauf endet mit 1; die Daten der Quellen sind dann schon übernommen. Seit der Nachprüfung zu E46 bleibt die Aktualisierung offen: Jede Quelle mit Änderungen trägt ihren Lauf in `pipeline_meta.katalog_offen` ein, in derselben Transaktion wie ihre Daten, also auch dann, wenn der Lauf vor dem Aufruf abbricht. Jeder folgende Lauf ruft die Funktion auch ohne eigene Änderungen auf, bis sie gelingt (im Bericht `katalog.nachgeholt` mit den früheren Läufen). So lange meldet `--status` WARNING. **Leser der View:** `REFRESH` ohne `CONCURRENTLY` braucht eine `ACCESS EXCLUSIVE`-Sperre. Solange die Anforderung wartet (höchstens 10 s, `laden.KATALOG_WARTEN`), stehen auch neue Abfragen auf die View hinter ihr an. Während des `REFRESH` selbst warten alle Leser der View. Auf den Bestandstabellen hält er keine solche Sperre. Der GeoServer ist nicht Teil davon (Antwort 75).

**Kennzahlquellen** (Tabellen wie `dashboard_data_de`) brauchen `ziel.pflicht` mit der Wertspalte, etwa `pflicht: [wert, zeitbezug]`: Ohne sie überschreibt eine Zelle ohne Wert („-“, „.“) den bisherigen Wert mit null, gemeldet nur als Hinweis. `leere_auslassen` (CSV) wirkt nur zusammen mit `zahl_felder`; fehlt `zahl_felder`, bricht die Quelle mit Meldung ab (E42).

**Neue Quelle** (Codex-Prüfung 05.11., B14): 1. Eintrag in `config/quellen.yaml` (Quelle und `ziel`). 2. Rechte: `docker compose run --rm einrichten` als Administrator; erst danach darf die Importrolle in neue Tabellen oder Spalten schreiben (geringste Rechte, E10), ohne diesen Schritt endet der Lauf mit `permission denied`. In der Datenbank der TH ist das ein administrativer Schritt, keine reine Konfiguration. 3. `--probelauf` und Bericht ansehen (keine dauerhaften Änderungen an den Fachdaten, jede Transaktion wird zurückgerollt, nur eine Sequenz einer Zieltabelle zählt weiter; geschrieben werden der Prüfbericht `<lauf>-probelauf.*` und, wo die Quelle ihn nutzt, der Cache der Downloads). Dasselbe nach jeder geänderten Zuordnung (`ziel`) und nach einem Update, das `pipeline_meta` erweitert (der Lauf meldet das mit klarer Meldung, E40).

**Im Compose-Setup von MOSIDI** (die vorgesehene Betriebsform, Antwort 36 der TH) kommt keine eigene Datenbank dazu: `deploy/mosidi/docker-compose.pipeline.yml` hängt die Dienste `pipeline-einrichten` und `pipeline` an `brandenburg_db`. Ablauf und getesteter Stand: [deploy/mosidi/README.md](../deploy/mosidi/README.md).

**Docker-Rechte:** Wer Docker steuern darf, ist auf dem Rechner faktisch root. Die Begrenzung leistet der gehärtete Container (nur lesbares Dateisystem, keine Linux-Capabilities, keine Rechteausweitung, eigener Benutzer). Wer rootless Docker oder Podman nutzt, setzt in der Unit `Environment=DOCKER_HOST=…` bzw. nutzt `podman compose`; die Compose-Datei ist dafür nicht angepasst und vorher zu testen.

## Quellen und Abrufregeln

**robots.txt wird respektiert, mit einer benannten Ausnahme** (E48, Prüfung nach E48, E50): Jeder Rechner, den eine mitgelieferte Konfiguration abruft, ist gegen seine `robots.txt` geprüft; ein `Crawl-delay` wird über `rhythmus` und `pause_s` eingehalten. Die gesperrten Pfade aus der Tabelle unten stehen zusätzlich im Code (`ROBOTS_GESPERRT` in `pipeline/quellen.py`): Vor jeder Verbindung (Abruf, Dateiabruf, HEAD-Suche nach dem jüngsten Jahr) lehnt die Pipeline einen gesperrten Pfad ab, auch einen, den sie erst zur Laufzeit ermittelt (Link von der Seite eines Berichts, er zählt dann wie ein fremder Link). Verglichen wird der Pfad, den requests tatsächlich sendet, dekodiert, ohne Punktsegmente und mit einfachen Schrägstrichen (seit E50; `/a/../scrivito/` oder `/a/%2e%2e/scrivito/` sind `/scrivito/`). Keine Konfiguration kann die Sperrliste verkürzen.

**Ausnahme mit Namen: `robots_freigabe`** (E50, Entscheidung André vom 06.11.2026). Eine Quelle darf den Rechner ihrer eigenen Adresse (`url`, sonst `seite`, sonst `pfad`, wenn er eine Adresse ist) trotz Sperre abrufen, wenn sie eine benannte, nicht leere Freigabe trägt, etwa `robots_freigabe: "Vorgabe des Auftraggebers, Antwort 33 (VA-2026-536); Erlaubnis des BBSR wird in AP 1 schriftlich eingeholt"`. Nur ein Text zählt (`true`, eine Zahl oder Leerraum nicht). Die Freigabe gilt für den ganzen Rechner der eigenen Adresse, auch für andere Pfade und Folge-Links dorthin, und nur für diese Quelle; andere gesperrte Rechner (auch über Links von einer Berichtsseite oder Folge-Links dorthin) und andere Quellen bleiben gesperrt. Verglichen wird der Rechner, den requests tatsächlich anwählt; eine Adresse mit Anmeldedaten oder Rückstrich vor dem Rechner (`https://a.example\@b.example/`, dort lesen urlsplit und requests verschiedene Rechner) wird vor jeder Verbindung abgelehnt (Nachprüfung zu E50). Der Grund darf keine Steuerzeichen oder Zeilenumbrüche enthalten (sonst bricht der Lauf und `--ziele` vorher ab). Jede Nutzung steht im Bericht des Laufs, auch im Abbruchbericht nach SIGTERM oder Strg+C (Warnung „robots.txt von … sperrt …; abgerufen mit der Freigabe dieser Quelle (robots_freigabe): …“ und `info.robots_freigabe` mit Rechner, gesperrtem Pfad und Grund), im Textbericht und im Protokoll je Lauf (`pipeline_meta.quellenlauf`, Spalte `warnungen`; ein abgebrochener Lauf und `--probelauf` schreiben dort keine Zeile, dann steht die Freigabe nur im Bericht); `--ziele` nennt den Rechner und die Freigabe als Kommentarzeile (unten). Die Freigabe entfernen, sobald der Anbieter widerspricht; dann bricht die Quelle wieder vor jeder Verbindung ab.

**INKAR** (`www.bbr-server.de`, `Disallow: /`): Antwort 33 der TH verlangt den automatischen Abruf per URL. Die ausgelieferten `config/quellen.yaml`, `config/pruefkonfiguration.yaml` und `config/deutschland.yaml` setzen dafür die Freigabe oben; der Regelbetrieb lädt INKAR also ohne Dateiablage: HEAD-Suche nach der jüngsten Jahresdatei, Download nach `cache/`, danach nur bei Änderung (If-Modified-Since). Die Erlaubnis des BBSR holen wir in Arbeitspaket 1 schriftlich ein. Zusätzlich, nicht als Voraussetzung, bleibt die abgelegte Datei, etwa für Prüfläufe ohne Netzabruf: die Gesamtdatei unter `cache/` ablegen (als `/app/cache` in `docker-compose.yml` und im Overlay für MOSIDI eingehängt) und `PIPELINE_INKAR_DATEI=/app/cache/inkar_2025.zip` in `.env` setzen (beide Compose-Dateien reichen die Variable an den Dienst `pipeline` durch) oder `datei:` in der Quelle; dann ruft INKAR nichts ab, und der Bericht vermerkt „robots_freigabe konfiguriert, nicht genutzt“. Ohne Freigabe und ohne Datei endet INKAR mit `FEHLER` („robots.txt … sperrt automatische Abrufe; INKAR nicht abgerufen“), ohne den Rechner abzurufen; die übrigen Quellen laufen. Wir selbst rufen `www.bbr-server.de` nicht ab: Tests nutzen Attrappen, unsere Belegläufe die abgelegte Datei.

**Regel für eigene Läufe** (Nachprüfung zu E50): Jeder Lauf, den wir selbst starten (Belegskripte, Testcompose, Prüfläufe, Agenten), setzt `PIPELINE_INKAR_DATEI` auf die abgelegte Datei unter `cache/` oder lädt keine INKAR-Quelle (`--nur`). Die ausgelieferte Konfiguration trägt die Freigabe für den Regelbetrieb der TH; ein Lauf nach dem Schnellstart ohne diese Variable ruft `www.bbr-server.de` ab. Die Belegskripte bis E47 bauen den aktuellen Stand ohne die Variable und brechen deshalb gleich zu Beginn als abgelöst ab; nur `beispielberichte/pruefstand-2026-11-06-e49/` setzt sie und ist der Weg für neue Belegläufe. Der Abruf per URL ist nur mit Attrappen getestet, nicht gegen den echten Rechner.

**Neue Quellen nur nach Prüfung:** vor dem ersten Abruf `robots.txt` und Nutzungsbedingungen des Rechners lesen (auch für einen einzelnen Test- oder Probeabruf, HEAD oder Statusabfrage) und das Ergebnis hier eintragen. Die Pipeline liest `robots.txt` zur Laufzeit nicht selbst; die Prüfung ist ein Schritt bei der Aufnahme und bei jeder geänderten Adresse.

**Zeitbudget je Quelle** (`zeitbudget_min`, E50): Jede Quelle hat ein Zeitbudget, Standard 30 Minuten, oben in der Konfiguration für alle und je Quelle einstellbar (positive Zahl bis 35 791, dem Höchstwert von `statement_timeout` in PostgreSQL, sonst bricht der Lauf vor dem ersten Abruf ab; Obergrenze seit der Nachprüfung zu E51). Geprüft wird vor jeder Anfrage, je gelesenem Block eines Downloads, in langen Schleifen der Adapter (INKAR alle 65 536 Zeilen, GeoJSON je Objekt, je Datensatz beim Einlesen) und zwischen den Schreibschritten. Ein Download zählt zum Budget seiner Quelle; die INKAR-Quellen setzen deshalb ein eigenes Budget (der Standard von 30 Minuten ist an Läufen mit abgelegter Datei bemessen): die Lieferkonfiguration im Vollumfang `zeitbudget_min: 240` (E51: gemessen 146,5 min ohne Download, dazu rund 430 MB per URL; Folgelauf und Zielrechner damals nicht gemessen, daher rund 60 % Zuschlag; am Abgabestand nach E51 gemessen: Erstlauf INKAR 129,4 min, Folgelauf 158,2 min, Zielrechner und Download weiter nicht), Prüfkonfiguration und `deutschland.yaml` mit fünf Kürzeln `zeitbudget_min: 90`. Eine abgebrochene Teildatei wird gelöscht, ein Fortsetzen gibt es nicht; auf einer Leitung, die den Download nicht im Budget schafft, scheitert INKAR bei jedem Lauf, dann das Budget der Quelle erhöhen (und `TimeoutStartSec` im Blick behalten) oder die Datei ablegen. Gemessen ist der Download per URL nicht (nur Attrappen). Überschreitet eine Quelle es, wird ihre Transaktion zurückgerollt (der alte Stand bleibt), der Bericht führt sie als `FEHLER` mit „ZeitbudgetUeberschritten: Zeitbudget von … min überschritten“, ohne Meldungsentwurf an den Anbieter, und die nächste Quelle läuft. Kein Abbruch der Pipeline von außen (Signal, Thread): Eine Anfrage zwischen zwei Prüfpunkten läuft zu Ende (Zeitlimit 60 s je Block); um so viel kann eine Quelle ihr Budget überschreiten. Für den ganzen Lauf gilt `TimeoutStartSec` der systemd-Unit (7 h seit E51, über der Summe der Zeitbudgets der Lieferkonfiguration; bei mehr Quellen oder größeren Budgets mitziehen, `tests/test_betrieb.py` prüft die Summe).

**Zeitgrenzen der Datenbank je Quelle** (E51, Befund K1 des Prüfberichts vom 07.11.2026): Bis E51 lief eine Datenbankanweisung ohne Grenze zu Ende; wartete sie auf eine Sperre, die eine andere Sitzung auf der Zieltabelle hielt (Wartung, Schemaänderung, lange Transaktion), hielt sie alle folgenden Quellen bis zum Abbruch des ganzen Laufs auf. Jetzt setzt die Pipeline zu Beginn der Transaktion jeder Quelle und an jedem Prüfpunkt zwischen den Schreibschritten nur für diese Transaktion (`set_config(…, true)`, wie `SET LOCAL`): `statement_timeout` = Rest des Zeitbudgets und `lock_timeout` = kleinerer Wert aus Rest und `db_sperre_max_s` (Standard 300 s, oben für alle oder je Quelle; positive Zahl bis 2 147 483, sonst Abbruch vor dem ersten Abruf). Bricht PostgreSQL eine Anweisung daran ab, wird die Transaktion der Quelle zurückgerollt (alter Stand bleibt), der Bericht führt sie als `FEHLER` mit „ZeitbudgetUeberschritten: Zeitbudget/Datenbank-Zeitgrenze überschritten (lock_timeout …)“ bzw. „(statement_timeout …)“, ohne Meldungsentwurf an den Anbieter, und die nächste Quelle läuft; die blockierte ist beim nächsten Lauf wieder fällig (kein Erfolg). Ein Datenbanktest hält mit einer zweiten Sitzung eine Sperre auf der Zieltabelle (`ACCESS EXCLUSIVE` und `SHARE`): Die Quelle bricht nach der Grenze ab, die nächste lädt. Grenzen: Die Einleseanweisung (`COPY` in die Eingangstabelle) bleibt offen, solange der Adapter liest, daher ist `statement_timeout` der Rest des Budgets und kein kleinerer fester Wert. Ein Schreibschritt aus mehreren Anweisungen setzt die Grenze nicht vor jeder Anweisung neu; jede darf bis zum Rest am letzten Prüfpunkt laufen, zusammen also länger. `transaction_timeout` (ganze Transaktion) gibt es erst ab PostgreSQL 17, unterstützt wird auch 16. Erkannt wird ein Abbruch durch `lock_timeout` an der Fehlerart, einer durch `statement_timeout` daran, dass das Budget der Quelle aufgebraucht ist (Rest unter 1 s), nicht am Text der Servermeldung, der `lc_messages` des Servers folgt (Nachprüfung zu E51; bis dahin galt nur der englische Text). Ein Abbruch von Hand (`pg_cancel_backend`) in der letzten Sekunde des Budgets zählt deshalb als Zeitgrenze. Ein Datenbanktest lässt eine Anweisung länger schlafen als das Budget (`pg_sleep`): PostgreSQL bricht sie am Ende des Budgets ab.

**Nullmenge und bestätigte Leerlieferung** (E50): Liefert eine Quelle 0 Objekte, hält sie an und der alte Stand bleibt, auch mit abgeschaltetem Rückgang-Schutz (`max_rueckgang: null`). Ist die Leerung beim Anbieter bestätigt (etwa eine Attributquelle, die es nicht mehr gibt), gibt `--leerlieferung QUELLE "GRUND"` sie für genau diesen Lauf frei: Die Quelle wird abgeglichen, ihre bisherigen Zeilen werden gelöscht (soweit das Ziel löschen darf, Raumdaten nie, E35), und der Bericht nennt Freigabe und Grund (`leerlieferung`, Warnung). Nicht bei einem unvollständigen Abruf und nicht bei fehlenden Feldern: Dann hält die Quelle trotz Freigabe an. Die Freigabe steht nie in der Konfiguration, damit sie nicht in den nächsten Lauf mitwandert. Wird die Quelle im selben Lauf nicht geladen (`--nur` für eine andere Quelle, nicht fällig nach Rhythmus), nennt der Bericht die ungenutzte Freigabe mit Grund (`leerlieferung_ungenutzt`, Nachprüfung zu E50). Beispiel: `docker compose run --rm pipeline --nur QUELLE --leerlieferung QUELLE "Anbieter bestätigt Leerung, Mail vom …"`.

## Firewall und Proxy

Welche Rechner der Container erreichen muss, sagt die Pipeline selbst, ohne Datenbank:

    docker compose run --rm --no-deps pipeline --ziele

Ausgabe mit `config/quellen.yaml` (seit E50):

    download.statistik-berlin-brandenburg.de:443
    isk.geobasis-bb.de:443
    www.bbr-server.de:443
    www.statistik-berlin-brandenburg.de:443
    # robots.txt-Freigabe: www.bbr-server.de (Quelle inkar_gemeinden): Vorgabe des Auftraggebers, Antwort 33 (VA-2026-536); Erlaubnis des BBSR wird in AP 1 schriftlich eingeholt

`www.bbr-server.de` (INKAR) steht darin, weil die INKAR-Quelle ihn mit ihrer Freigabe abruft (oben, Quellen und Abrufregeln); die Zeile mit `#` nennt die Freigabe und lässt sich in Skripten mit einem Filter auf `#` überspringen. Mit `PIPELINE_INKAR_DATEI` (abgelegte Datei) fehlen Rechner und Kommentarzeile, ohne Freigabe ebenso.

Nach jeder Änderung an `config/quellen.yaml` die Liste neu erzeugen. Weitere ausgehende Verbindungen braucht der Lauf nicht.

**Änderungskarte und Drittverbindungen** (E38): Die Karte ist eine einzelne HTML-Datei; die Kartenbibliothek Leaflet steht eingebettet darin (`pipeline/vendor/leaflet-1.9.4/`, BSD-2-Clause, Prüfsummen im Test). In der Grundeinstellung lädt die Seite beim Öffnen **nichts** aus dem Netz, sie zeigt die Objekte ohne Hintergrundkarte. Hintergrundkarten von Dritten nur ausdrücklich, oben in der Konfiguration:

    karte:
      hintergrund: [basemap, luftbild]   # basemap.de (sgx.geodatenzentrum.de), Luftbild DOP20 (isk.geobasis-bb.de)

Dann holt der Browser dessen, der die Seite öffnet, Kacheln von diesen Servern (nicht der Pipeline-Server). Ganz ohne Karte: `karte: false` oben in der Konfiguration, dann entsteht keine Kartendatei. `karte: false` bei einer einzelnen Quelle lässt nur deren Objekte weg.

**Was die Karte zeigt und was nicht** (Codex-Prüfung 05.11., B12): Die Karte ist eine Übersicht, nicht der Bericht. Je Quelle zeigt sie höchstens 20 000 Objekte (`karte_max_objekte`, Änderungen in der Regel zuerst, unveränderte danach; Grenzfall: zurückgehaltene und unverändert übernommene Zeilen sortieren bei Quellen mit eigener Geometrie wie Änderungen, E49); was darüber hinausgeht, steht nur im Bericht und in `pipeline_meta.aenderung`. Quellen ohne eigene Geometrie (Kennzahlen in `dashboard_data_de`) erscheinen nicht je Zeile, sondern je Gebiet zusammengefasst (Fläche aus der Gebietstabelle, Anzahl neu/geändert/gelöscht als Attribute). Zahlen gelten deshalb nur aus dem Bericht.

**Proxy:** Darf der Server nur über einen Proxy ins Internet, in `.env` setzen:

    HTTPS_PROXY=http://proxy.example.org:3128

Die Datenbank (`db`) und `localhost` gehen nie über den Proxy. Weitere Ausnahmen über `NO_PROXY`. Ein falscher Proxy zeigt sich im Bericht als `ProxyError` je Quelle.

**Kennung gegenüber den Anbietern:** Die Pipeline nennt sich in den Server-Logs der Anbieter `geodaten-import-pipeline` mit Adresse des Repositorys (User-Agent). Im Betrieb in `.env` Name und Kontakt des Betreibers setzen, damit sich ein Anbieter bei Problemen melden kann, statt zu sperren:

    PIPELINE_KENNUNG=MOSIDI-Import (+https://github.com/MOSIDI-ORG; kontakt@example.org)

## Überwachung

**Zustand für Icinga, Nagios, Checkmk oder Zabbix:**

    docker compose run --rm --no-deps pipeline --status --max-alter-h 26

Gibt eine Zeile mit Messwerten aus und endet mit 0 (OK), 1 (WARNING: eine Quelle fehlgeschlagen oder angehalten, deren alter Stand bleibt, oder unvollständig abgerufen, dann wurde nichts gelöscht und der nächste Lauf holt sie erneut; auch wenn alle geladenen Quellen unvollständig sind, mit Rhythmen oft nur eine, E44), 2 (CRITICAL: kein lesbarer Bericht, letzter Lauf älter als `--max-alter-h` Stunden, technisch abgebrochen, oder keine geladene Quelle ok oder unvollständig, also alle fehlgeschlagen oder angehalten) oder 3 (UNKNOWN). WARNING auch, wenn der Katalog (`source_granularities`) nicht aktualisiert werden konnte (E46). Ein unvollständiger Abruf zählt wie im Quellenverzeichnis nicht als Erfolg (E42). Der Messwert `quellen_ok` zählt nur vollständig abgerufene Quellen, `unvollstaendig` die übrigen mit Status ok; `pipeline_meta.lauf` führt dieselbe Zahl in der Spalte `unvollstaendig`. Warnungen wertet `--status` nicht aus, auch nicht ein nicht geschriebenes Quellenprotokoll, Stand-Archiv oder einen nicht geschriebenen Meldungsentwurf: Die Daten der Quelle sind dann übernommen, der Lauf meldet OK und endet mit 0; die Warnung steht im Bericht und die Ursache im Journal (E45). Beispiel:

    GEODATEN OK - Lauf 20261030T192603Z, 1 Quellen ok | quellen_ok=1 fehler=0 angehalten=0 unvollstaendig=0 alter_h=0.0;;26

`--status` bewertet den jüngsten Bericht in `berichte/`. Laufen mehrere Konfigurationen, jede mit eigenem `berichte`-Ordner betreiben oder alle Quellen in eine Konfiguration nehmen.

**Technischer Abbruch** (E34, E38; genauer gefasst nach der Codex-Prüfung vom 05.11., B10): Abgefangene Laufzeitfehler, bevor der Bericht fertig ist (Datenbank nicht erreichbar, `pipeline_meta` fehlt oder ist zu alt, Sperrdatei nicht anlegbar, `SIGTERM`), hinterlassen einen Bericht mit `abbruch`, **wenn der Berichtsordner beschreibbar ist**; `--status` meldet dann CRITICAL, der Lauf endet mit 2. Scheitert schon das Schreiben dieses Berichts (etwa bei voller Platte), wird der Fehler darüber nicht gemeldet, es bleiben stderr und Rückgabe 2. Ausbleibende Berichte, Prozessabbrüche (`SIGKILL`, Absturz des Containers, Neustart des Rechners) und volle Platten erkennt die Überwachung von außen: `--status` über die Altersgrenze (`--max-alter-h`) und der Rückgabewert der systemd-Unit (`OnFailure`). Bricht er erst danach ab (etwa beim Quellenverzeichnis), wird `abbruch` im fertigen Bericht nachgetragen. Scheitert die Laufzeile in `pipeline_meta.lauf` oder kommt die Datenbank nach einem Abriss während des Laufs nicht zurück (`DatenbankWeg`), steht der Bericht mit den Quellen bis dahin, und `abbruch` steht auch im Textbericht und in der Karte (E44, E45); beim Quellenverzeichnis nur im JSON. Grenzen: Ist die Konfiguration unlesbar, ist der Berichtsordner unbekannt; ist der Berichtsordner nicht beschreibbar, geht kein Bericht. Dann steht die Ursache auf stderr (Journal), der Lauf endet mit 2, und `--status` meldet UNKNOWN (Konfiguration unlesbar) bzw. spätestens nach `--max-alter-h` CRITICAL. Ein zweiter Start, während ein Lauf die Sperre hält, endet mit 1 und schreibt bewusst keinen Bericht: Er wäre jünger als der des laufenden Laufs und verdeckte ihn in `--status`. Seit E46 gilt die Sperre zusätzlich datenbankweit (`pg_advisory_lock` auf der Verbindung des Laufs): Auch ein Start mit anderem Berichtsordner, aus einem anderen Container oder von einem anderen Rechner gegen dieselbe Datenbank endet so. Reißt die Verbindung ab, endet die Sperre mit ihr; der Lauf nimmt sie mit der neuen Verbindung wieder, und hat sie inzwischen ein anderer Lauf, endet er als technischer Abbruch (`DatenbankWeg`). Gegen `SIGKILL` hilft nur die Altersgrenze. Dass `docker compose run` ein `SIGTERM` von systemd an den Container weiterreicht, ist vorgesehen, aber in einem echten Timeout noch nicht nachgestellt.

**Wiederholung nach unvollständigem Lauf** (E38): War der letzte Lauf einer Quelle unvollständig, ist sie beim nächsten regulären Lauf fällig, auch wenn ihr Rhythmus noch nicht abgelaufen ist (Hinweis „Wiederholung“ im Bericht, nur wenn sie ohne die Wiederholung „nicht fällig“ gewesen wäre). Das gilt auch, wenn der unvollständige Lauf mit `--alle` oder `--nur` erzwungen war und davor ein junger Erfolg lag.


- **Exit-Code:** Der Timer-Dienst endet mit Fehler, wenn eine Quelle fehlgeschlagen, angehalten oder unvollständig ist oder der Lauf technisch abbricht. Dann startet `geodaten-import-fehler.service` und schreibt eine Zeile mit Priorität `err`:

      journalctl -p err -t geodaten-import

  Eigene Benachrichtigung (Mail, Chat, Ticket) per `systemctl edit geodaten-import-fehler.service` ergänzen, Beispiel steht in der Datei.
- **Letzter Lauf:** `systemctl status geodaten-import.service`, Ausgabe des Laufs mit `journalctl -u geodaten-import.service`.
- **Berichte:** `berichte/<lauf>.txt` (lesbar), `<lauf>.json` (maschinenlesbar), `<lauf>-karte.html` (Karte), `quellenverzeichnis.md` (Stand aller Quellen mit letztem erfolgreichem Abruf).

| Hinweis „source_granularities gibt es in dieser Datenbank nicht“ oder Warnung „Katalog … nicht aktualisiert“ | Die View fehlt (Hinweis, kein Fehler), oder `REFRESH` scheiterte: Der Eigentümer der Funktion darf die View nicht aktualisieren (`einrichten` warnt: „katalog_aktualisieren() gehört …“), oder die View war länger als 10 s gesperrt (E46, Nachprüfung) | Bei der Warnung von `einrichten` deren Abhilfe ausführen: als Superuser `ALTER FUNCTION pipeline_meta.katalog_aktualisieren() OWNER TO <Eigentümer der View>`. `einrichten` nur erneut auszuführen ändert den Eigentümer nicht. Bei einer Sperre nichts tun: Der nächste Lauf holt die Aktualisierung nach, auch ohne Änderungen (`pipeline_meta.katalog_offen`); bis dahin bleibt `--status` auf WARNING. Sofort von Hand: als `pipeline_import` `SELECT pipeline_meta.katalog_aktualisieren();`, danach `DELETE FROM pipeline_meta.katalog_offen;` |
| Lauf endet mit 1: „Die Sperre der Pipeline auf derselben Datenbank … hält Sitzung <pid>“ | Eine andere Sitzung hält die datenbankweite Sperre (E46). Meist ist das ein zweiter Lauf, auch mit anderem Berichtsordner oder von einem anderen Rechner. Den Schlüssel kann aber jede Rolle mit Zugang zur Datenbank nehmen (`pg_advisory_lock` braucht kein Recht), in der Datenbank von MOSIDI also auch `mosidi_lesen` oder ein Anwendungsnutzer der Plattform. Nach einem halboffenen Verbindungsabriss kann es auch die alte, serverseitig noch lebende Sitzung der Pipeline selbst sein | Mit `SELECT pid, usename, application_name, backend_start, state FROM pg_stat_activity WHERE pid = <pid>` die Sitzung bestimmen. Ist es ein Lauf, warten. Sonst als Administrator `SELECT pg_terminate_backend(<pid>)`. Hält eine fremde Sitzung die Sperre dauerhaft, endet jeder Lauf mit 1 ohne Bericht, und `--status` meldet erst nach `--max-alter-h` CRITICAL |
| `permission denied for language plpgsql` bei Quellen mit Geometrie | Die Datenbank hat PUBLIC das Recht `USAGE ON LANGUAGE plpgsql` entzogen; die Pipeline legt je Quelle eine temporäre Funktion an (unlesbare Geometrien je Objekt auslassen, E38). `einrichten` warnt davor | Als Eigentümer der Sprache: `GRANT USAGE ON LANGUAGE plpgsql TO pipeline_import` |
| Quelle `FEHLER`, „Zieltabelle … fehlt“ oder „Spalten fehlen in …“ | Zuordnung `ziel` passt nicht zum Schema der Datenbank | `ziel` in `config/quellen.yaml` an die Tabelle anpassen; das Schema der Bestandstabellen nicht ändern |
| Warnung „… nicht gelöscht: Abruf war nicht vollständig“ | Der Dienst hat Objekte ohne ID oder Geometrie geliefert oder weniger als gemeldet | Nichts zu tun; beim nächsten vollständigen Abruf wird gelöscht. Hält es an, Meldungsentwurf an den Anbieter |
| Warnung „Kachel …: Vollständigkeit nicht belegt“ | WFS ohne Gesamtzahl (`numberMatched`): Die Folgeseite der Kachel brachte nichts Neues oder war nicht abrufbar, Seiten ohne feste Reihenfolge brachten weniger verschiedene Objekte als gezählt, bzw. bei WFS 1.1.0 mehr Treffer als geliefert oder keine Trefferzahl (E47, Nachprüfung). Der Abruf gilt als unvollständig, es wird nichts gelöscht, und ohne Erfolg lädt die Quelle bei jedem Lauf (Rhythmus greift erst nach einem vollständigen Abruf) | Nur bei „mehr Treffer als geliefert“ (WFS 1.1.0) hilft es, `kachel_m` bzw. `max_je_kachel` zu verkleinern. Blättert der Dienst nicht (Folgeseite ohne neues Objekt oder nicht abrufbar, meist bei `ImplementsResultPaging=FALSE`), lässt sich Vollständigkeit nur mit `numberMatched` oder `CountDefault` belegen: beim Anbieter anfragen; kleinere Kacheln helfen nicht |
| Warnung „… Datenzeilen ohne gültigen Gebietsschlüssel übergangen (Zeilen …)“ oder „… Datenzeilen mit n statt m Spalten“ | Statistiktabelle mit `zeilen_muster`: Eine Zeile mit der Form einer Datenzeile hat keinen Schlüssel in gültiger Form (`schluessel_form`, am rohen Feld, also auch mit Leerzeichen oder Tab am Rand), eine Zeile passt erst ohne Leerzeichen oder Anführungszeichen zum Gebiet, eine gewählte Zeile hat eine andere Spaltenzahl, oder die meisten gewählten Zeilen haben eine andere Spaltenzahl als die Kopfzeile (E47, Nachprüfung). Nichts wird gelöscht. Nicht erkannt: ein Schlüssel, der nach dem Schaden nur aus Ziffern besteht (fehlende oder doppelte Ziffer) | Datei beim Anbieter prüfen; ist die Schlüsselform neu und gültig, `schluessel_form` erweitern |
| Warnung „… Zeilen nach dem Datenbereich sind nicht eindeutig als Fußzeilen erkennbar (Zeilen …)“ | Statistiktabelle mit `zeilen_muster`: Nach der letzten Datenzeile steht eine Zeile, die keine erlaubte Fußzeile ist (E51, Befund K2): mehr als ein Feld mit Inhalt oder ein Feld nicht in der ersten Spalte, ein Feld, das mit einem Schlüssel beginnt, oder eine Zahl bzw. ein Fehlwert nach dem ersten Feld. Meist eine beschädigte letzte Datenzeile; bis E51 verschwand sie still und ihr bisheriger Wert wurde gelöscht. Nichts wird gelöscht | Zeile in der Datei ansehen. Ist es eine echte Fußzeile des Anbieters mit mehreren Feldern oder mit einem Schlüssel am Anfang (etwa „2014 Gebietsreform“), sie mit `fuss_muster` der Quelle erlauben (regulärer Ausdruck auf die ganze Zeile, etwa `'^Quelle:;'` oder `'^2014 Gebietsreform'`; seit der Nachprüfung zu E51 auch für ein erstes Feld in Schlüsselform). Das Muster eng fassen: Passt es auch auf Datenzeilen (`'.*'`), bleibt eine abgeschnittene letzte Datenzeile stumm. Gesperrt bleibt trotzdem eine Zeile mit einer Zahl, einem Fehlwert oder einem Schlüssel nach dem ersten Feld. In XLSX gibt es kein `fuss_muster` |
| XLSX-Quelle `angehalten`: „Blätter fehlen“, „keine Kopfzeile mit …“ oder „Beschriftung … steht mehrfach“ | Statistischer Bericht (Typ `xlsx`) mit geändertem Aufbau: ein genanntes Blatt fehlt (`blaetter`), eine Spaltenbeschriftung aus `schluessel` oder `werte` ist in den ersten 30 Zeilen eines Blatts nicht zu finden (verglichen ohne Leerzeichen, Zeilenumbrüche und Fußnotenzeichen) oder eine Wertspalte ist nicht eindeutig (E48). Alter Stand bleibt | Bericht beim Anbieter ansehen; ist der Aufbau gewollt neu, `blaetter` bzw. die Beschriftungen in `config/quellen.yaml` anpassen, `--probelauf --nur QUELLE` |
| Warnung „… Datenzeilen ohne gültigen Schlüssel“, „… mit verschiedenen Schlüsseln in den Schlüsselspalten“, „… Schlüssel mehrfach geliefert“, „… Werte sind keine Zahl“, „Summe … weicht von der Summenzeile … ab“, „… Teilsummen weichen ab“ oder „… gehören zu keiner Teilsumme ihres Blatts“ (XLSX) | Eine Zeile mit Wert hat keinen Schlüssel nach `schluessel_form` (leer, Buchstabe, Leerzeichen, falsche Länge, Formel ohne gespeicherten Wert), eine Zeile ohne Wert hat in einer Schlüsselspalte etwas in Schlüsselform (etwa `12O60005`, `1206000`) oder einen Wert, der kein Text ist (seit E51, Befund K2), die beiden Schlüsselspalten unterscheiden sich, ein Schlüssel kommt zweimal, ein Wert ist Text oder keine endliche Zahl, die Summe der gewählten Gemeinden passt nicht zur Landeszeile (`summe`) oder zur Kreissumme ihres Blatts (`summe.teilsummen`), oder eine Gemeinde steht im Blatt eines anderen Kreises. Nicht erkannt: ein Schlüssel, der in beiden Spalten zu einem anderen gültigen, bisher nicht vorhandenen Schlüssel desselben Kreises wird (nur der Hinweis auf eine Gemeinde ohne Gebiet), und vertauschte Werte innerhalb eines Kreises | Datei beim Anbieter prüfen (Blatt und Zeile stehen in der Warnung); Meldungsentwurf |
| XLSX-Quelle `FEHLER`: „Kein Link nach datei_muster“, „mehrere Links für dieselbe Ausgabe“, „Zeitbezug … nicht gefunden“ bzw. „mehrdeutig“, „Blatt … nicht lesbar“ | Die Seite des Berichts nennt die Datei anders oder gar nicht, nur auf einem fremden Rechner oder einem per robots.txt gesperrten Pfad, eine Zelle ist für openpyxl nicht lesbar (etwa „NaN“ als Zahl), oder der Stichtag steht nicht (eindeutig) im Titel bzw. in der Fußnote (E48) | Seite im Browser ansehen; `datei_muster`, `link_rechner` oder `zeitbezug.muster` anpassen; bis dahin ersatzweise die Datei ablegen (`pfad`, oben) |

## Aufbewahrung der Berichte

Ohne Angabe löscht die Pipeline nichts. In `config/quellen.yaml`:

    aufbewahrung_tage: 180

löscht nach jedem regulären Lauf Laufdateien (Bericht, Karte, Meldungsentwürfe, Stand-Archiv), die älter sind. Es bleiben immer stehen: der jüngste reguläre Bericht, auch wenn er älter ist (er ist der Vergleichsstand für den nächsten Lauf), und `quellenverzeichnis.*`. Der Bericht des Laufs nennt unter `aufgeraeumt`, wie viele Dateien gelöscht wurden.

**Stand-Archiv** (optional, `archiv: true`): Für jede Quelle, die sich in einem Lauf geändert hat, legt die Pipeline ihren neuen Stand als `berichte/archiv/<lauf>/<quelle>.geojson.gz` ab, mit Lizenz und Lauf an jedem Objekt. Damit lässt sich später sagen, welcher Datenstand einer Auswertung zugrunde lag, ohne die Tabellen zu versionieren. Die Aufbewahrungsfrist gilt auch dafür.

## Sicherung und Wiederherstellung

Ein Neuimport ersetzt keine Wiederherstellung (Codex-Prüfung 05.11., B9): Raumdaten, die eine Quelle nicht mehr liefert, bleiben nach Antwort 74 in den Tabellen stehen (`loeschen: false`), und das Änderungsprotokoll in `pipeline_meta` (Register mit Quellschlüsseln, Änderungen je Lauf, Stand je Quelle) entsteht nur aus den Läufen selbst. Beides kann kein neuer Abruf wiederherstellen. Zu sichern sind deshalb:

| Was | Warum | Wie |
|---|---|---|
| **die ganze Bestandsdatenbank**, einschließlich `public` (mit zurückbehaltenen Raumdaten und den Daten anderer Importe der Plattform) und `pipeline_meta` | einziger vollständiger Stand; `pipeline_meta` gehört dazu, sonst gelten nach einer Rücksicherung alle Zeilen als fremd („übernommen“) und Löschungen der Quellen kommen nicht mehr an | `docker compose exec db sh -c 'pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB"' > sicherung.dump`, zeitlich nach dem Lauf, nicht während (ein Lauf schreibt je Quelle in einer Transaktion, `pg_dump` sieht einen konsistenten Stand) |
| `.env` | Passwörter der Rollen; vertraulich behandeln | wie andere Geheimnisse des Servers |
| `config/quellen.yaml` | welche Quellen wie geladen werden | mit dem Repository |
| `berichte/` | Laufberichte und Quellenverzeichnis, mit Stand-Archiv auch frühere Datenstände | Dateisicherung |

`cache/` muss nicht gesichert werden: Die Dateien darin lädt die Pipeline bei Bedarf neu.

Wiederherstellen: leeres Volume, `docker compose up -d db`, `pg_restore` der Sicherung, danach `docker compose run --rm einrichten` (ergänzt, was eine neuere Fassung in `pipeline_meta` braucht, und setzt Rechte). Ohne Sicherung bleibt nur der Neuimport mit `--alle`: Er bringt den aktuellen Stand der Quellen, aber nicht die zurückbehaltenen Raumdaten und nicht das Änderungsprotokoll; der erste Bericht zeigt dann alle Objekte als neu.

## Updates

Dependabot schlägt wöchentlich Updates für Pakete, Images und Actions als Pull Request vor; die Prüfkette (`pruefen.sh`) läuft darauf automatisch.

1. Pull Request ansehen. Prüfung grün und keine Hauptversion der Datenbank: zusammenführen.
2. Auf dem Server: `git pull && docker compose build pipeline`
3. `docker compose run --rm pipeline --probelauf`, Bericht ansehen.
4. Zurück bei Problemen: `git checkout <voriger Commit> && docker compose build pipeline`.

**Hauptversion von PostgreSQL/PostGIS** (etwa 16 auf 18) nie per automatischem Update: Ein bestehendes Datenverzeichnis passt nicht zur neuen Hauptversion. Vorher sichern, dann mit `pg_upgrade` oder Sicherung und Wiederherstellung umziehen.

## Passwörter wechseln

Am einfachsten: `IMPORT_PASSWORD` in `.env` ändern und `docker compose run --rm einrichten` ausführen; es setzt
das Passwort neu und schickt dabei nur den SCRAM-Hash an den Server (E39). Von Hand in psql mit `\password`, das
ebenfalls nur den Hash sendet, nicht mit `ALTER ROLE … PASSWORD '<neu>'` (das Passwort stünde bei einem Fehler
oder mit `log_statement` im Server-Log):

    docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
    \password pipeline_import

Dann `IMPORT_PASSWORD` in `.env` ändern. Für die Leserolle `mosidi_lesen` entsprechend `LESE_PASSWORD`, für die Plattform dort ebenfalls nachziehen.

## Datenschutz

Nach unserem Stand und nach Kenntnis der TH (Antwort 68) verarbeitet die Pipeline in der Beispielkonfiguration keine personenbezogenen Daten: ALKIS vereinfacht enthält Gebäude ohne Eigentümer, VG250 Verwaltungsgrenzen, INKAR und die amtliche Statistik zusammengefasste Werte je Gebiet. Vor dem Einsatz neuer Quellen mit der zuständigen Stelle prüfen. Die Pipeline schickt keine importierten Daten an Dritte; sie ruft nur die konfigurierten Quellen ab, und Meldungsentwürfe an Anbieter versendet nur ein Mensch. Die Änderungskarte lädt in der Grundeinstellung nichts aus dem Netz (Leaflet eingebettet, keine Hintergrundkarte). Nur wenn `karte.hintergrund` gesetzt ist, holt der Browser beim Öffnen Kacheln von basemap.de bzw. der LGB; dabei sehen diese Server die IP-Adresse des Betrachters und den Kartenausschnitt. `karte: false` oben in der Konfiguration schaltet die Kartendatei ganz ab (E38).
